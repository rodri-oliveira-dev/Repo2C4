# Deterministic LikeC4 generation

`LikeC4Emitter.Emit(ArchitectureModel)` converts one validated v1 architecture model into exactly three in-memory UTF-8-compatible text sources:

- `specification.c4`
- `model.c4`
- `views.c4`

The emitter performs no repository reads or writes, starts no processes, contacts no network or AI provider, and never opens or changes a pull request. Hosts such as the CLI can decide later where, whether and under which overwrite policy to persist these strings.

## Contract and notation mapping

The v1 `ArchitectureModel` remains the source of truth. Generation does not infer additional elements or relationships.

| v1 contract | LikeC4 output |
| --- | --- |
| `actor` | `actor` element kind |
| `softwareSystem` | `softwareSystem` element kind |
| `container` | `container` nested below its `parentId` software system |
| `ArchitectureRelation` | directed `source -> destination` relationship, using the v1 description as the title |
| `requiresReview` | `#requires-review` plus `reviewStatus` and `reviewReason` metadata |
| evidence IDs | sorted `evidenceIds` metadata |
| architecture ID | `architectureId` metadata |

The specification defines `actor`, `softwareSystem`, `container` and the amber `requires-review` tag. The tag is deliberately visible in generated diagrams so a hypothesis is not rendered as if it were a confirmed assertion.

No relationship kind or protocol is invented. The v1 relation contract has no separate relationship-kind/protocol field, so generation keeps the reviewed interaction text in the relationship title and preserves review/provenance metadata.

## Identifiers and hierarchy

v1 IDs permit `.`, while LikeC4 reserves `.` for fully qualified hierarchy. The emitter therefore replaces `.` with `_` in each local LikeC4 identifier.

Normalization is not allowed to hide ambiguity. If two architecture IDs in the same LikeC4 scope normalize to the same identifier, generation fails with `likec4.identifierCollision`. For example, sibling IDs `payments.api` and `payments_api` are rejected instead of receiving arbitrary suffixes.

Root actors/software systems share the model scope. Containers use the normalized identifier of their reviewed parent system as the FQN prefix. Contract validation runs before generation, so missing parents, duplicate IDs, missing relation endpoints and invalid v1 identifiers fail before any output is returned.

## Escaping and text safety

Human-facing names, relationship descriptions and review reasons are always emitted as quoted LikeC4 strings.

- `"` and `\` are escaped.
- CRLF and CR are normalized to LF.
- Unicode is preserved.
- LF and tab are kept inside the quoted string.
- Unsupported control characters cause `likec4.textControlCharacter` rather than being written into the DSL.

This keeps braces, tags, arrows and other DSL-looking input inside a string instead of allowing it to create a new statement.

## Determinism

Generation uses ordinal ordering for elements, relationships and evidence references and always emits LF line endings. Collection enumeration order therefore cannot change generated bytes.

Checked-in golden outputs live under `examples/likec4-golden/` for:

- the reviewable Acme C1 fixture;
- the reviewable Acme C2 fixture;
- the library-only partial C2 fixture.

Core tests compare all three generated files byte-for-byte after normalizing the checked-in fixture line endings to LF. The library-only model remains partial: generation does not add a container or relation merely to complete a C2 view.

## Views

A C1 model produces one `c1` view titled `C1 - System Context`. A C2 model produces one `c2` view titled `C2 - Containers`.

Views include exactly the elements already present in the reviewed `ArchitectureModel`, in stable order. C1 cannot contain containers because the v1 contract validator rejects them. C2 does not discover or synthesize missing containers.

## API example

```csharp
using Repo2C4.Core.Contracts;
using Repo2C4.Core.LikeC4;

ArchitectureModel model = ContractJson.DeserializeModel(json);
IReadOnlyList<LikeC4GeneratedFile> files = LikeC4Emitter.Emit(model);

foreach (LikeC4GeneratedFile file in files)
{
    Console.WriteLine(file.FileName);
    Console.WriteLine(file.Content);
}
```

Writing these files and validating them with the official LikeC4 CLI are intentionally separate responsibilities. CLI validation is introduced by issue #11; persistence/overwrite behavior is introduced by issue #12.
